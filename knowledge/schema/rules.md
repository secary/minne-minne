# Schema v1 规则

## 身份、命名与路径

- `schema_version` 必填，当前值是字符串 `"1"`。
- `id` 使用 `type:slug`，类型限 `ship`、`equipment`、`mechanic`、`quest`、`map`、`event`、`source`；`slug` 使用小写英文字母、数字、下划线和短横线，首字符为字母或数字，完整 ID 最长 128 个字符。ID 不随标题、别名或语言变化；已发布的 ID 不重新分配给其他实体。
- frontmatter 的 `type` 必须与 ID 前缀一致。文件路径按类型映射到目录，并使用 `<slug>.md`，不使用标题构造路径。
- `title` 是非空显示名；正文恰有一个一级标题，且与 `title` 一致。日文名、中文名、简称和昵称放在 `aliases`，避免重复别名和与标题相同的别名。别名是检索入口，不是实体 ID。
- 舰娘的不同改造形态使用不同 ID，以 `form_of` 关系指向所属舰娘；一个形态至多有一个 `form_of`，目标也必须是 `ship:`。不能把形态差异混成同一组无适用条件的属性。
- 页面只使用契约中声明的字段，未知字段视为错误。前后空白不构成有效名称或证据。

## 元数据

每页必须提供 `schema_version`、`id`、`type`、`title`、非空 `sources` 和 `applicability`。`aliases`、`relations` 与 `conflicts` 缺省为空列表。

`relations` 的每项含 `target` 与 `kind`，后者取 `related`、`form_of`、`requires`、`unlocks` 或 `obtained_from`。关系有方向，含义分别为相关、所属舰娘、依赖、解锁和获取来源。关系不能指向自身，同一关系不重复声明。正文可以按需补充说明和证据。

`applicability` 包含以下信息：

| 字段 | 约定 |
| --- | --- |
| `scope` | 必填；`permanent`（常驻）、`historical_event`（历史活动）或 `unknown`（待确认） |
| `event_id` | 活动页面 ID；`historical_event` 时必填 |
| `valid_from` / `valid_until` | 结论适用的起止日期，格式 `YYYY-MM-DD`；同时存在时开始不得晚于结束 |
| `difficulties` / `stages` | 难度与阶段列表，缺省为空；正文须说明具体限制 |
| `notes` | 可选非空补充说明，特别注明范围未确认的原因 |

`permanent` 范围不能设置 `event_id`；难度和阶段列表内不重复。来源抓取时间、来源修订时间属于快照元数据，不代替 `valid_from` 或 `valid_until`。`unknown` 不代表已经确认适用于全部时期；同一页存在多种条件时，正文中的每条结论仍需保留自己的条件。

## 来源与正文引用

`sources` 是本页实际使用的证据列表，每项包含：

| 字段 | 约定 |
| --- | --- |
| `id` | 本页唯一的引用标签，例如 `c1`；小写字母开头，后续使用小写字母、数字、下划线或短横线，最长 64 个字符 |
| `source_id` | 来源稳定 ID，例如 `wikiwiki-kancolle`；不是站点显示名 |
| `snapshot_id` | 数据库 `raw_snapshots.id` 的 UUID；不是存储目录名、页面 ID、抓取任务 ID 或“最新版本” |
| `locator` | 快照中的具体段落或表格定位标识；后续由正文解析器提供并写入证据目录 |
| `quote` | 可选非空原文摘录，用于审阅；不能替代 `locator` |

正文在相应事实旁使用 `[@c1]` 引用，不将该标记写成 Markdown 脚注定义。标签必须在本页 `sources` 中定义，所有声明的证据都应在正文或冲突记录中使用。同一来源、快照与定位组成的证据不使用不同标签重复声明。多个事实的证据不同，应分别引用；仅列出整页 URL 不足以支撑关键数值、公式或掉落结论。

例如，`sources` 中标签为 `c1` 时，正文可写“待原文核实后填入结论及其适用条件。[@c1]”。该句仅展示语法，不表示存在已确认的游戏事实。

正文关联使用 `[[ship:akagi]]`，需要显示名时使用 `[[ship:akagi|赤城]]`。链接依赖稳定 ID，不以标题、别名或文件相对路径替代。发布前应对完整候选版本校验目标存在；草稿中尚未生成的目标应在后续编译中补齐。

原始快照不可覆盖。来源证据目录需能证明 `snapshot_id` 属于相应 `source_id`，且 `locator` 存在于该快照解析产物。目录只证明结构上的可定位性，不能证明结论忠实于证据；数值、单位、引文和适用条件仍需原文核对。

## 冲突与待确认

- 无证据时明确标记资料不足，不生成确定结论。掉落统计必须保留样本时间、样本量、难度、节点和统计口径，不能把估计值描述为固定概率。
- 新旧资料不一致时先检查时间、阶段、难度、改造形态等条件是否不同；可并存的历史结论应保留各自范围。
- 无法按适用条件解释的分歧写入 `conflicts`，用 `summary` 描述分歧，并用 `citations` 引用至少两条本页证据。
- 新冲突默认 `status: unresolved`，不能填写 `resolution`。未解决冲突会阻止发布前校验通过，草稿保留分歧及双方证据。
- 处理后改为 `status: resolved`，必须填写非空 `resolution` 说明依据与处理结果，保留原始证据。不能只删除不同意见或把较新抓取时间当作裁决理由。

## 更新与版本

1. 来源更新创建新快照，不修改旧快照或把旧引用悄悄改成“最新”。
2. 后续编译器根据“快照 → Wiki 页面”依赖定位受影响页面；本阶段通过显式 `sources` 为依赖提取提供契约，尚不写入数据库依赖表。
3. 在独立候选目录更新正文、引用、关系和适用范围。标题改动保留 ID；涉及实体合并、拆分或 ID 迁移时显式处理旧链接与历史追溯。
4. 删除或停用来源后重新评估受影响结论；仅移除引用不能证明结论仍然成立。
5. 通过结构、引用、关联和冲突校验，再交给后续完整发布流程。当前校验命令不写入 Wiki、不生成发布版本，也不修改搜索索引。
6. 编译任务将来应记录 `schema_version` 与规则代码版本。字段、必需小节、引用语法或规则语义发生不兼容变化时，升级 Schema 版本并提供显式迁移；旧页面不能通过修改版本字符串伪装为已迁移。

应用仓库保留 Schema 与规则的代码历史；知识仓库保留页面变更历史。模型不能通过资料中的指令修改规则、执行任意文件操作或写入原始快照；API 密钥和其他服务端配置不得进入 frontmatter、正文、模板或知识 Git 历史。
